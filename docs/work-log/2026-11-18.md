## 工作記錄與程式解說

### 1. BLE 資料接收路徑確認

App 的主要 BLE 接收實作位於 [`lib/services/esp32_ble_service.dart`](../../lib/services/esp32_ble_service.dart)：

1. `connect()` 確認 BLE 支援狀態並在 Android 請求執行期權限。
2. 掃描韌體名稱 `CC1101_BLE` / `ThermoCam_BLE`，再連接裝置。
3. 透過韌體 service UUID 找到 service，再依 characteristic UUID 找到資料 characteristic。
4. 啟用通知，將每次收到的通知交給 `handleNotification()`。
5. `handleNotification()` 能將分段 JSON bytes 組成完整物件，解析成 `Cc1101DiagnosticSample`，並送入共用 `HardwareDataMonitor`；同時支援既有 132-byte 二進位感測封包。

韌體新版使用的主要服務與特徵 UUID 與 App 已支援的 ThermoCam UUID 相同。因此，本次針對這個新版的資料格式，沒有新增另一套 App BLE 傳輸流程；主要必要的 App 端連線修正是 Android 執行期權限處理。

新版韌體目前將感測 JSON 放在主要 characteristic 中傳送，這比舊版單獨建立 Wi-Fi list characteristic 的做法更符合 App 目前的訂閱架構。舊版若只收到主 characteristic、不另外訂閱 Wi-Fi characteristic，Wi-Fi AP 清單就不會到達 App。

`lib/main.dart` 的責任較上層：建立 `HardwareConnectionService`，透過 `HardwareConnectionScope` 提供給頁面。它不直接掃描 BLE，也不直接解析通知。

### 2. Android BLE 權限與連線錯誤處理

[`lib/services/esp32_ble_service.dart`](../../lib/services/esp32_ble_service.dart) 新增 `_requestAndroidBlePermissions()`：

```dart
final sdkInt = (await DeviceInfoPlugin().androidInfo).version.sdkInt;
final permissions = sdkInt >= 31
    ? [Permission.bluetoothScan, Permission.bluetoothConnect]
    : [Permission.locationWhenInUse];
final statuses = await permissions.request();
```

這段程式依 Android 版本採取不同權限策略。Android 12 起 BLE 掃描與連線需要「附近裝置」權限；較舊 Android 的 BLE 掃描則仰賴定位權限。使用者拒絕時會回報明確的錯誤，不再繼續當作已取得權限。

[`android/app/src/main/AndroidManifest.xml`](../../android/app/src/main/AndroidManifest.xml) 同步宣告：

- `BLUETOOTH_SCAN` / `BLUETOOTH_CONNECT`。
- 限制在 Android 11 以下使用的 `BLUETOOTH` / `BLUETOOTH_ADMIN`。
- BLE 硬體 feature。
- 舊版掃描所需的定位權限仍保留。

[`lib/views/hardware/hardware_monitor_view.dart`](../../lib/views/hardware/hardware_monitor_view.dart) 的連線命令不再使用 `fallbackToSimulator: true`。連線失敗現在維持錯誤狀態並向使用者顯示錯誤，不會以熱圖模擬資料掩蓋連線問題。

此行為變更反映一個診斷原則：**硬體連線失敗時，模擬資料不能呈現成硬體資料已正常接收。**

### 3. Arduino 多感測器整合版

今日提供的程式已整合到 [`arduino/cc1101_ble_diagnostic/cc1101_ble_diagnostic.ino`](../../arduino/cc1101_ble_diagnostic/cc1101_ble_diagnostic.ino)。雖然沿用專案既有的 sketch 路徑，內容已由原本單獨的 CC1101 BLE 測試程式替換為整合版。

新版包含下列資料路徑：

- **AMG8833**：I2C 讀取 8×8 熱像像素，建立 `thermal` 及 `amg8833.pixels` 欄位。
- **CC1101**：RadioLib 接收封包，累積收到／遺失封包數、RSSI、LQI 與 CRC 狀態；另有環境 RSSI 讀取流程。
- **VS1838B / IR LED**：接收紅外線協定或原始脈衝狀態，產生 IR 偵測資料。
- **Wi-Fi**：背景掃描附近 AP，以 BSSID 為索引套用 Kalman RSSI 濾波，再估算距離。
- **BLE**：每秒產生一份 JSON，拆成 20-byte 通知區塊傳送；若 Wi-Fi 已連線，另外以 UDP 廣播同一份 JSON。

主要 BLE 名稱與 UUID：

```cpp
constexpr char BLE_NAME[] = "CC1101_BLE";
constexpr char BLE_SERVICE_UUID[] =
    "6e400001-b5a3-f393-e0a9-e50e24dcca9e";
constexpr char BLE_CHARACTERISTIC_UUID[] =
    "6e400003-b5a3-f393-e0a9-e50e24dcca9e";
```

這與 App 的 `Esp32BleService` 支援的名稱／UUID 相符。韌體 `sendBleChunkedJson()` 將序列化後的 UTF-8 JSON 切成小塊，再逐塊呼叫 characteristic notify。App 必須先啟用通知，並把收到的 bytes 組回完整 JSON，才能交給資料模型。

JSON 的主要結構包含：

```json
{
  "device_name": "CC1101_BLE",
  "rf_rssi": -70.0,
  "cc1101": {
    "rssi": -70.0,
    "received_packets": 0,
    "lost_packets": 0,
    "per": 0.0
  },
  "wifi_count": 0,
  "wifi_networks": [
    { "ssid": "example", "rssi": -60.0, "distance_m": 1.6 }
  ]
}
```

此範例只列出部分欄位以說明格式，並非完整封包；實際數值由韌體感測結果決定。熱像欄位依感測器狀態為 64 個數值或 `null`，不會是空陣列。韌體 AP 清單改用 `wifi_networks`，距離欄位用 `distance_m`，兩者符合 App [`lib/models/cc1101_diagnostic_sample.dart`](../../lib/models/cc1101_diagnostic_sample.dart) 的 Wi-Fi AP JSON 解析欄位。App 可同時顯示 AP 數量與清單中的 SSID、RSSI、距離。

### 4. Wi-Fi 掃描狀態修正

Arduino `handleWifi()` 新增 `wifiResultsProcessed` 旗標：

```cpp
if (r >= 0 && !wifiResultsProcessed) {
  // 處理剛完成的掃描結果
  wifiResultsProcessed = true;
}

if (r != WIFI_SCAN_RUNNING &&
    wifiResultsProcessed &&
    now - lastScanDone >= SCAN_GAP_MS) {
  WiFi.scanNetworks(true, true, false, 120);
  wifiResultsProcessed = false;
}
```

`scanComplete()` 回傳非負值時代表有一輪掃描結果。旗標使結果只被處理一次；等待掃描間隔後，程式刪除舊結果並開始下一輪非同步掃描。這避免每次主迴圈都把同一批已完成的結果視為新結果，也防止掃描工作沒有持續重新啟動。

Wi-Fi 憑證在專案程式碼中保留為空字串。`setupWiFi()` 遇到空 SSID 時會跳過連線，但仍維持 station 模式以便掃描 AP；`sendUdpJson()` 只有在 Wi-Fi 狀態為 connected 時才送 UDP。換言之，Wi-Fi 憑證不是 BLE 廣播或 BLE 感測資料傳送的前置條件。

### 5. 感測器資料語意與更新頻率

- `updateThermal()` 約每 250 ms 更新熱像；若感測器不存在且 `SIMULATE_WHEN_NO_AMG` 設為 `0`，韌體不會偽造熱像陣列，而會在 JSON 中回報熱像不可用。
- `processRf()` 只在 CC1101 的 packet-ready 中斷旗標成立時讀取封包，並更新封包 RSSI、LQI、CRC 與計數器。
- `updateEnvironmentRssi()` 約每 500 ms 嘗試讀取接收環境 RSSI。這是 CC1101 射頻讀值；不是手機讀取的 BLE 連線 RSSI，也不能直接視為已收到某個 RF 封包的 RSSI。
- `processIr()` 結合 IRremote 協定解碼與 GPIO 脈衝統計；每秒傳輸後會重設單次偵測旗標與 IR code/protocol。
- 主迴圈每 1 秒封裝並傳送一次 JSON；非連線狀態下每隔約 5 秒安排一次 BLE 掃描，以計算附近 BLE 裝置數。
- Wi-Fi AP 清單最多放入 8 筆，縮短 JSON 長度，避免每秒傳輸過大的 notify 分段。

`sendBleChunkedJson()` 對每一段呼叫 NimBLE 的 `notify(data, length)`。不需要先把整份較長的 JSON 寫入 characteristic value，因此移除原稿中先呼叫完整 `setValue(payload)` 的步驟，避免把大型 payload 當成單一 characteristic value；通知內容仍是逐段 JSON bytes，由 App 組包。

JSON 範例中的熱像欄位未展開：感測器可用時，`thermal` 是 **64 個數值**的陣列（不是空陣列）；感測器不可用時為 `null`。App 的模型會驗證陣列長度，避免把不完整熱圖當成正常資料。
